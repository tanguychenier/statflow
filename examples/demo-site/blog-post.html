How cookieless analytics actually works — a technical deep-dive

By Elena Voss · April 10, 2025 · 12 min read

Most write-ups on "privacy-first analytics" spend a lot of ink explaining why you should stop using cookies and almost none on how the alternative actually works in production. This post fills that gap. We'll trace a single event from the moment a user clicks a button on your site all the way through to a row in ClickHouse — and explain every design decision along the way.

The problem with cookie-based analytics

Traditional analytics platforms like the incumbent market leaders use a persistent first-party cookie (or a third-party one if you haven't self-hosted) to stitch page views from the same browser into a single user session. This is elegant and accurate, but it has serious drawbacks:

  • Cookies are personal data under GDPR, ePrivacy, CCPA, and most other privacy regulations, so you need explicit opt-in consent before setting them.
  • Consent rates vary wildly — typically 40–70% — meaning your analytics are incomplete by design.
  • Safari's Intelligent Tracking Prevention (ITP) deletes first-party cookies after 7 days, further skewing long-term retention data.
  • Ad blockers block the analytics scripts outright. uBlock Origin has 40M+ users.

The result: cookie-based analytics consistently under-count traffic by 20–40%, depending on your audience. If your users are developers or privacy-conscious, the gap is even larger.

Session identification without cookies

If we can't use a persistent identifier stored in the browser, how do we stitch events into sessions? Lumen uses a combination of three signals, none of which are personal data under EU law:

  1. IP address hash (salted, daily-rotated). We hash the visitor's IP together with a daily salt that changes at midnight UTC. The raw IP is never stored; only the hash is. Because the salt rotates every 24 hours, the hash cannot be used to track a user across days.
  2. User-agent string hash. Combined with the IP hash, this produces a "daily fingerprint" that is stable within a session but not across days or devices.
  3. Referrer and URL. Session boundaries are inferred from referrer transitions and a 30-minute inactivity timeout, exactly as Universal Analytics defined sessions.
The key insight is that you don't need to identify a user across days — you only need to stitch events within a ~30-minute window to produce meaningful session-level metrics.

The tracker script

The Lumen tracker (lumen.js) is intentionally tiny — under 3 kB gzipped. It does three things on load:

  1. Records the initial pageview by sending a POST request to the ingestion endpoint with the current URL, referrer, screen size, and a timestamp.
  2. Listens for history.pushState / popstate to detect SPA navigation and fires additional pageview events accordingly.
  3. Exposes window.lumen.track(eventName, properties) for custom events.

No cookies are set. No localStorage is written. The tracker is purely fire-and-forget. 

// Minimal custom event example
window.lumen.track('checkout_started', {
  plan: 'growth',
  billing_cycle: 'annual',
  currency: 'USD',
});

The ingestion pipeline

Events arrive at an HTTP endpoint backed by a lightweight Go service. The service does the following synchronously, in under 1 ms of added latency:

  1. Validates the payload schema (rejects malformed events with a 400).
  2. Extracts the client IP from the X-Forwarded-For header, hashes it with today's salt, then discards the raw IP.
  3. Enriches the event with GeoIP data (country, region) from a local MaxMind database — no external requests.
  4. Parses the User-Agent string to extract browser, OS, and device type.
  5. Writes the enriched event to a Kafka topic.

A Kafka consumer reads from the topic and batch-inserts rows into ClickHouse using the INSERT INTO … FORMAT JSONEachRow API with a 1-second flush interval. ClickHouse's columnar storage means even a full table scan over billions of rows completes in milliseconds for typical analytics queries.

Query layer

The Lumen dashboard queries ClickHouse directly. Here's the SQL behind the "unique visitors" metric for a given date range: 

SELECT
  toDate(timestamp) AS date,
  uniqExact(session_id)    AS sessions,
  uniqExact(daily_visitor_hash) AS visitors
FROM events
WHERE
  site_id = 'your-site-id'
  AND timestamp BETWEEN {start:DateTime} AND {end:DateTime}
GROUP BY date
ORDER BY date;

uniqExact gives an accurate count (not an HLL approximation) and still returns in under 10 ms on a 100M-row table, thanks to ClickHouse's aggressive parallelism.

What about accuracy vs. GA4?

In our internal benchmarks on sites with mixed audiences, Lumen consistently reports 15–30% more sessions than GA4 for the same period. The gap is wider on developer-focused sites (where ad-blocker adoption is high) and narrower on e-commerce sites with a broad consumer audience.

This isn't Lumen over-counting — it's GA4 under-counting due to blocked scripts and unconsented cookie drops.

Conclusion

Cookieless analytics is not a compromise — it's often a more accurate picture of reality. By combining daily-salted IP hashing, user-agent fingerprinting, and session timeout logic, Lumen produces session data that is both privacy-safe and more complete than what most cookie-based tools deliver today.
